# nvim-zh 架构演进与优化实施设计

本设计规定 Neovim 0.12+ 上的显示投影、配置提交、可选包加载和工具链发布方案。先修复原始数据边界与同步一致性，再降低大词库的启动和重绘成本。实现以官方 Neovim 0.12.6 为对照基线，各平台按实测能力公布支持。

## 设计决定

| 议题 | 决定 |
| --- | --- |
| 显示接缝 | 只在最终渲染入口应用译文。证据不足时沿用上游显示，保留现有原文查询。 |
| 公开契约 | 保留 Lua 函数、用户命令、配置键和回调结果结构。现有 SDK 1 索引、附件和登记统一由同一个读取和验证入口处理。 |
| 历史包 | 已发布附件和现有安装继续可用。历史包可显式选择和离线回滚。自动推荐只列出与当前目标有兼容证据的版本。 |
| 热配置 | 以操作代次提交最后一份完整有效状态。能力不支持可以独立降级。配置、登记读取或 native 恢复硬失败时作废候选。 |
| 性能 | 先移除重复解析、建表和整表读取，再按已验证的工具需求准备词库。保持 JSON 和当前包格式，派生索引可以从已验证输入重建。 |
| 构建与证据 | 每个翻译来源有唯一编辑入口。生成物先增加按诊断 ID 的可审差异，达到字节再现条件后一次切换工具链生成入口。 |
| 扩展顺序 | 先处理同一进程内的多项目、多 LSP 客户端及 DAP 会话，再扩展已验证的 LLVM 发行版及第三方补全。 |

命令、快捷键、用户输入、源码、项目正文、构建退出状态、跳转、LSP/DAP 原始协议对象和应用回调数据均由原有系统持有。网络只用于显式包管理或维护端取源。所有投影依赖本地已验证资源，保留摘要、失败回退和可复现生成。 [当前架构](architecture.md) · [公开 API](api.md) · [适配与发布契约](adapter-system-design.md)

## 基线与验收口径

审计源码基线为 `main@da04760`，可选包索引基线为 `origin/packs@a7c9bab`。复现使用官方 Neovim 0.12.6、Linux x86_64、glibc 2.44 和摘要匹配的 LLVM 23.1.5。重建的 Clang 0.1.0、clangd 0.1.2、clang-tidy 0.1.0 附件与索引摘要一致。完整工具链门禁通过，报告含 91,654 个合成及实测样本。旧版 clangd 0.1.1 到 0.1.0 的离线回滚和损坏回退分别通过。 [工具链身份](../manifests/toolchain.json) · [覆盖统计与复跑](toolchain-coverage.md) · [基线验证记录](verification.md)

| 本机基线 | 负载和读数 |
| --- | --- |
| 启动 | 每组 5 个新进程，关闭 native，首轮创建主包快照，其余复用。无包、仅 clangd、Clang 与 clangd 同时启用的 `setup()` 中位数分别为 58、245、410 ms，GC 后进程 RSS 分别为 21.3、57.6、73.5 MiB。 |
| 词库 | Clang 33,543 条，clangd 33,016 条。两个正式附件共 18,051,460 字节。首次查词建索引分别约 25 和 45 ms，首次访问典型大模板桶各约 6–7 ms。两个域开始查词后 Lua 堆约 60.5 MiB。 |
| 诊断批次 | 1,000 条诊断启停对照。启用时虚拟文本、quickfix、loclist 的 P50 / P95 分别为 18.2 / 56.7、15.1 / 53.8、13.8 / 64.4 ms。关闭时 P95 分别为 24.9、5.4、4.6 ms。 |
| 编译器列表 | 750 个真实 Clang 诊断、3,001 个解析项。打开 quickfix 的 P95 为启用 27.6 ms，关闭 1.0 ms。首个单错误构建含投影 155–173 ms，关闭 21–23 ms。 |

性能复验固定二进制和附件摘要，使用新的临时 XDG 目录及 `PYTHONDONTWRITEBYTECODE=1`。为启动分别记录第一次快照发布、复用快照的五进程数据、首次查词及首次模板匹配。为批次记录至少三组交替启停数据，每组 30 次诊断刷新、50 次 500 项补全转换。CLI 使用重复的合法函数声明，每个函数含一个缺分号的 return，以 `clang -fsyntax-only -ferror-limit=0` 生成诊断，并分别计时构建和开列表。比较 P50、P95、进程 RSS 与 Lua 堆，记录组内最大值和兼容回退。性能目标适用于同机同负载的相对比较。 [测试环境隔离](../tests/run/lib/env.sh#L9) · [UI 观察基准](../benchmarks/ui_attach.lua#L20)

## P0 显示层与运行时一致性

### 诊断列表与 LSP 原始数据

当前 `diagnostics.setup_lists()` 将译文送入 `opts.format`，Neovim 以 formatter 的输出建立 quickfix 项。现有契约因此断言 `getqflist().items[].text` 为中文，`raw().raw_text` 也会读到译文。当前 LSP 进度 wrapper 把译后的副本交给上游 handler，`LspProgress` 和 `client.progress` 因此收到中文进度。保持输入对象原样只覆盖这一链路的第一段，验收还要检查数据的下游消费者。 [诊断投影](../lua/nvim-zh/diagnostics.lua#L322) · [现有列表契约](../tests/contract/diagnostics/diagnostic_display_spec.lua#L47) · [LSP 进度投影](../lua/nvim-zh/lsp.lua#L93)

1. **诊断列表交给 Neovim 创建。** 接缝可通过调用内的 formatter 观察参与排序的诊断及原 formatter 的返回值，观察函数按原值返回，`nil` 消除该项，异常照常传播。无用户 formatter 时保持上游的默认内容。仅在能确认目标 Window、列表 ID、创建代次和解析项对应关系时安装该列表专属的 `quickfixtextfunc`。重复位置、排序或来源歧义按项回退。存在用户 formatter 所有权冲突时沿用用户显示。
2. **编译器和诊断列表共用投影约束。** 列表 ID、`changedtick`、局部 formatter 和投影记录必须匹配。保持原始条目及列表 context、`user_data`、索引、位置、标题、跳转和命令结果。按 Neovim 安装 formatter 后的实际 `changedtick` 记录代次。启停、回滚、翻译覆盖和列表切换触发失效或显示刷新，保留 Window、选择和视图。清理前重新核对所有权。
3. **LSP 原 handler 与数据订阅者接收上游对象。** 移除经过通用 `buf_request_all()` 回调的数据投影。进度从原始数据派生面板显示，原生 `LspProgress` 和 `client.progress` 保持原文。自定义 `fileStatus` handler 收到原参数，自有状态保存可追溯的原始状态。可核实的通知、悬浮、签名、选择器或补全 formatter 继续翻译其显示字段。选择回调返回原 action，文档正文、插入范围和附加编辑原样传递。
4. **原文查询保持现有入口。** `:NvimZhRaw` 读取当前列表的原文并在有证据时附上来源和代码。`:NvimZhDiagnosticRaw` 查询当前源文件行的原 LSP 诊断。旧行为中的列表译文和进度译文消费者迁至显示入口，随修复发布记录这一行为纠正。

验收以真实诊断列表、CLI 列表和 LSP handler 为主。同一记录启停后比较原始数据、用户 formatter 调用次数和错误、列表排序与选中项、跳转、进度队列、事件和外部回调。另测重复行、一条诊断被过滤、保留外部 formatter、异步返回到旧列表、不同客户端同名诊断以及 unknown source。PTY 对照验证中文显示或明确英文回退。 [编译器列表投影范式](../lua/nvim-zh/compiler.lua#L316) · [原文命令](../plugin/nvim-zh.lua#L16) · [LSP 对照入口](../tests/workflows/clang_toolchain.lua#L43)

### 热配置提交和取消

一次同步应消费一份基础配置、一个配置文件候选及一组固定的资源和包登记证据。当前 native 完成后先提交再判断硬失败，包登记读取错误也可在 session 层被忽略。取消回调能在清理旧代次时重入，导致新代次的订阅被清理或检查回调丢失。 [运行时提交](../lua/nvim-zh/runtime.lua#L150) · [session 应用](../lua/nvim-zh/session.lua#L10) · [包登记同步](../lua/nvim-zh/packs.lua#L134) · [健康检查调度](../lua/nvim-zh/health.lua#L123)

| 阶段 | 写入和可见性 |
| --- | --- |
| 准备 | `runtime` 获取操作令牌和校验输入。保留已提交的配置、活动目录、Help 和包选择。native 可以在唯一临时位置准备 locale。后台准备产物在应用前重新核对令牌和所有权。 |
| 应用 | `session` 在协调器的当前代次应用候选。资源实现与适配入口继续冻结。提交时再次核对待替换的对象和已验证快照，native 绑定与 MO 哨兵探针维持现有保护。 |
| 提交 | 发布准备好的状态文件及活动内存引用，随后更新最后有效 JSON 层和状态快照。事件与完成回调在状态稳定后投递。无变化的显式刷新仍满足公开 loader 的刷新语义。 |
| 失败 | 配置校验、包登记树读取、资源或 native 恢复硬失败作废候选，按所有权恢复可恢复的旧状态。实际恢复失败继续报告 `restore_failed` 并反映真实 native 状态。某个外置包快照损坏时报告该包的激活失败并使用仍经验证的上一个版本。 |
| 停止 | 先使旧令牌失效，摘除其 timers、订阅和队列并完成清理，再交付取消通知。回调发起的新操作拥有独立令牌，旧路径无法删除它的状态。 |

普通平台不支持、外部拥有 native 状态或可独立降级的显示面，按能力报告 `degraded`。若候选资源会使现有 native 与已发布活动资源不一致，保留原有效资源，给出可操作的失败说明。外部函数、模块、locale 或绑定在准备期间变化时尊重新的拥有者。

`setup()`、`refresh()`、`check()` 和 `teardown()` 保留现有签名。回调保持既有 `task_id`、`status`、`error_code` 等字段，每个取到 ID 的回调恰好完成或取消一次。合并请求以最后实际应用的状态完成。各类 `NvimZhChanged` 通知都提供现有文档约定的 schema、generation 和 reason，沿用已有 reason 值，新增内容只放可选字段。状态查询继续读取快照，不执行探测或资源准备。 [公开同步与事件契约](api.md#refreshcallback) · [资源发布](../lua/nvim-zh/resources.lua#L121) · [native 恢复](../lua/nvim-zh/native_backend.lua#L120)

验收在原生准备、包登记读取、适配器应用、持久化提交和恢复处分别注入故障。覆盖取消回调内 `setup()`、取消检查内 `check()`、状态事件内再次刷新、旧 native 回调延迟、两次自动刷新合并。断言上一份有效状态、资源 ID、外部所有者、任务回调次数和重新 setup 后的订阅。 [现有生命周期测试](../tests/integration/runtime/lifecycle_spec.lua) · [native 异步所有权测试](../tests/integration/native/async_ownership_spec.lua)

### 选版、兼容证据与面板

当前已初始化的 clangd 23.1.4 会获荐无版本约束的 0.1.0，23.1.5 会获荐 0.1.2。CLI 列表中的目标存在检查只确认可执行文件。面板应区分登记、活动版本、目标已验证和当前显示实际生效。 [候选过滤](../lua/nvim-zh/packs.lua#L213) · [工具验证](../lua/nvim-zh/packs.lua#L542) · [包状态文案](../lua/nvim-zh/packs_ui.lua#L20)

- **选版单规则。** 自动推荐使用与目标相符且有明确声明的候选。工具尚未出现时浏览和显式安装可用，界面显示待验证。历史 clangd 0.1.0 可通过版本选择、明确版本的现有安装命令、导入或回滚继续使用，沿用该附件原来的匹配条件。保持已存在的安装选择，更新失败时按原代次规则保留或恢复。
- **证据按目标呈现。** CLI 分开显示已发现、已核对版本和二进制摘要、已验证该列表的输出接口。LSP 按客户端、Buffer 与方法标记兼容性。优先使用当前 Buffer 的客户端状态，有多客户端时分别列出原因。DAP 在相关界面按会话验证显示标签。
- **操作只在现有授权范围内执行。** 查看、筛选、状态查询与回滚使用本地登记或目录缓存。TUI 把刷新远程目录的按键标为「联网刷新」。保留包的选定、活动和上一版本，窄屏优先显示包名与当前原因，详情给出来源、最近失败和可执行的恢复操作。
- **登记代次仍由存储层控制。** 安装、暂停、卸载、回滚用观察到的代次提交。下载中发布源变化、并发选版或用户取消时重新核对任务身份与来源。同步以同一份登记快照检测 domain 冲突，冲突的包候选回退并报告原因，保留内置及用户注册的所有权。停用冲突包后恢复剩余候选。保持每包独立提交，增加真实双进程竞争测试。

验收使用来自本地的固定索引和真实历史附件。覆盖已验证与未验证的客户端并存、关闭客户端后切换项目、同版本不同摘要、目标晚加载、缩窄窗口、回滚及损坏旧包。明确版本的历史测试固定请求版本，最新版本测试从当前被验证的索引取期望值。 [现有包管理 PTY](../tests/e2e/test_packs_management.py#L78) · [历史附件测试](../tests/workflows/clang_pack_official.lua#L14) · [代次写入](../lua/nvim-zh/pack_store.lua#L102)

## P1 性能与可维护性

### 按需加载与索引生命周期

当前包加载会读取和解码完整附件、读取快照文件并解码内层词库，再调用 `prepare_sources()` 临时建表并返回调用者未使用的深拷贝。首次查询会再次建表。启动先只恢复用户选择和可确定的本地状态，大型纯数据包在首次相关工具使用时进入准备阶段。 [包加载](../lua/nvim-zh/pack_store.lua#L197) · [词库校验与读取](../lua/nvim-zh/catalog.lua#L213)

1. **将完整性和词库构建拆开。** 验证附件摘要、包内文件摘要、UTF-8、schema、重复键和兼容规则。一次准备仅建立一次索引或保有一份可构建索引的词库表示，安装发布时复用本次已经验证的候选。包登记只能用作预调度提示。面对历史包、未知类型或来源授权变化时，仍走同一个完整验证入口。
2. **按需触发。** 已配置的会话从实际 LSP 客户端使用、明确的 CLI 列表或显式 Lua 查词触发相应工具域。显示回调在准备中回退原文，可按同一代次重绘。公开 `translate()` 保持同步查词语义，只读取已登记的词库及已注册的用户目录。查词不启动 setup、联网或写盘，用户目录与本地覆盖保持现有优先级。需要在主线程应用的工作分段执行，异步结果提交前校验包摘要、有效配置和目标身份。
3. **派生索引随代次释放。** 安装、覆盖、选版变化使相应 domain 的索引失效，暂停和卸载释放大词库可达引用。未变化的 domain 不因其他域更新而重建，同时保留显式刷新对用户注册 loader 的已文档化行为。保留原先索引来源、占位符和歧义语义，支持按旧包快照重建。索引仍占内存时先减少持有副本，再依据测量决定有界释放。

验收在两份大包已启用但没有 Clang 工具使用时运行同样的五进程启动基准。目标是 `setup()` 中位数较 410 ms 下降至少 30%，GC 后 RSS 下降。独立记录首个相关工具出现到中文生效的时间，并验证准备期间、取消和换代后的原文回退。对 0.1.0、0.1.1、0.1.2 真实 clangd 附件和正式 Clang、clang-tidy 附件跑摘要、覆盖、导入、回滚及故障测试。 [当前工具包格式](../tools/pack_assets.py#L29) · [历史兼容口径](compatibility.md#诊断lsp-与外部工具)

### 匹配、列表重绘和工具来源

匹配层保留精确查询优先、受控锚定模板、占位符兼容、歧义回原文及 8,192 字节输入上限。先按已有稳定诊断代码或 context 过滤，再按固定文字缩小桶，并对同一候选去重。等价结果的条目 ID 和歧义选择保持稳定。只在长尾仍超预算时采用可重建的固定文字索引。当前 `diagnostics.match_forwarded()` 通过 `compiler.match_message()` 复用 clang-tidy 匹配，应抽出这部分纯函数，和维护端 Lua 复验一起切换到同一实现。 [匹配顺序](../lua/nvim-zh/engine.lua#L319) · [大模板桶](../lua/nvim-zh/engine.lua#L353) · [转发匹配](../lua/nvim-zh/diagnostics.lua#L105)

诊断的重复渲染复用同一发布批次内的纯匹配结果。缓存命中按来源、接口、词库和覆盖代次隔离。用户 formatter、回调、异常和缺失观察次数保持其公开契约。观察缓存维护精确的当前容量与有界淘汰，同样的脱敏标签与统计字段继续使用。原生补全可在单次转换内共享固定标签的匹配结果，原样返回无显示变化的候选。 [诊断 formatter](../lua/nvim-zh/diagnostics.lua#L158) · [观察缓存](../lua/nvim-zh/missing.lua#L29) · [补全转换](../lua/nvim-zh/lsp.lua#L197)

编译器先检查包可用性和用户 formatter 所有权。位置、输出格式和实际调用工具可核实后，才进行异步版本或摘要探测。工具路径、文件身份、列表 ID、`changedtick` 与代次共同约束结果。等待、过期或工具身份不足时保持原文。formatter 只读取必要的元数据和当前范围的有效投影，避免每次复制整个列表。活动包或覆盖变化时对仍可确认来源的旧列表重投影。已有用户列表、自定义格式、混合输出和间接构建沿用上游。

## 跨版本范围与停止条件

- **P0/P1 保持 SDK 1，P2 已按定量决策引入独立版本 SDK 2。** 保留 `schema`、目录结构、`catalog.json` 按 `(id, version, locale)` 去重规则、附件摘要和包登记格式。SDK 1 历史附件（`clang 0.1.0`、`clang-tidy 0.1.0`、`clangd 0.1.0/0.1.1/0.1.2`）无需重签，启停、导入、升级、损坏回退和离线回滚继续经过同一验证和状态路径。
- **P2 路线决策（P2.1 紧凑词库 + P2.2 路线 B SDK 2）：**
  - P2.1 通过两级映射 `exact[context][msgid] = msgstr`、惰性生成条目 ID、目录/桶内整数索引匹配缓存、非破坏性 `overrides` 覆盖层以及挂载后释放原始 `source` 表，在零格式变更下将双域 Lua 堆降低 70%+、存量 SDK 1 首用降低 31–35%。
  - 实测路线 A 派生缓存若每次重算权威 SDK 1 双文件摘要，首用仍达 70–74 ms 且磁盘放大至 3 份；若改为 `stat` 指纹守卫则弱化内容完整性校验。因此采用路线 B：以独立版本号（候选 `0.2.0`）发布单层紧凑 JSON（`manifest.sdk = 2`、`catalog.schema = 2`，纯数据包无冗余 `catalogs/zh_CN.json` 副本），在单一 `pack_store.lua` 边界内实现每次加载 100% SHA-256 + UTF-8 校验与 < 45 ms 首用。
  - 旧客户端沿用 `row.sdk == 1` 过滤继续安全选择 SDK 1；新客户端接受 `sdk == 1 or sdk == 2`，支持 SDK 2 ↔ SDK 1 损坏回退与离线回滚，不维护两套割裂运行时，也不执行 Lua 字节码。
- **扩大支持依据真实证据（单独立项）。** 多项目/多 LSP/多 DAP 并发补强、新 LLVM 发行版或 macOS/Windows CLI 摘要支持及第三方补全插件适配均单独立项，不与存储/加载重构混在一起。对来源不充分的项目正文、混合命令输出和 DAP 值，持续使用上游原文。
