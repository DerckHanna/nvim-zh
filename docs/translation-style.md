# nvim-zh 简体中文翻译规范

本规范适用于 Neovim 核心消息、项目界面、中文 Help，以及插件和开发工具的汉化资源。译者应在真实操作中确认文本的来源、用途和触发条件。译文要让用户在看到消息的地方读懂当前状态、对象和下一步操作，并能凭原有命令、标识符及错误码查阅参考资料。

## 简体中文写法

- 用自然、简洁的简体中文。把动作、结果或失败原因放在前面。普通提示省略可从界面推知的主语和礼貌套话。原文中的条件、范围、默认值、提示级别和后果都要译出来。
- 中文正文使用全角标点。汉字与相邻的英文词、命令或阿拉伯数字之间通常留一个 ASCII 空格，例如「按 `<CR>` 打开 Buffer」和「共 3 个文件」。中文标点前后通常直接相接。代码、路径、版本号和具有布局或解析语义的空白遵循原格式。
- 同一操作在菜单、通知和 Help 中使用一致的动词。标题和标签用短语，完整说明用短句。标签通常省略句末标点，确认问题使用问号。数字按语义选量词，例如「{count} 个文件」和「{count} 行」。用数字测试覆盖 0、1 和多个的情形。

正文的标点、空格及简明表达参考 Mozilla SUMO 简体中文团队的做法。语义和版面以 Neovim 实际显示为准。[Mozilla SUMO 简体中文本地化指南](https://mozilla-l10n.github.io/styleguides/zh-CN/sumo.html)

## 不同场景的译法

| 场景 | 写法 | 示例 |
| --- | --- | --- |
| 菜单、按键描述与标题 | 动作用动词短语，页面或结果用名词短语。相同的英文词按用途决定译法 | `Search` 动作译「搜索」，结果视图标题可译「搜索结果」 |
| 输入和确认 | 写清用户要输入的值，或确认的动作及对象。区分删除、移到回收站、关闭和退出 | `Delete {name}?` 译「删除 {name}？」 |
| 进度和结果 | 让阶段一眼可辨，保留计数和单位 | 「正在构建」「构建完成」「构建失败」 |
| 错误与诊断 | 写明失败动作或条件。原文提供原因和解决操作时一并译出。诊断详情可按既有入口取得原文 | `Cannot open {path}` 译「无法打开 {path}」 |
| Help 与操作指南 | 用可以直接执行的步骤说明条件、动作和预期结果。原有链接、命令、选项与示例供照着操作 | 「运行 `:checkhealth nvim-zh`，查看原生消息是否已启用。」 |

同一个英文字符串可能是不同动作、状态或概念。核对调用点再选译名。技术解释只采用已核实的信息。附加的中文排错指引应与上游译文分别标注，以便读者区分工具报错与项目说明。[Mozilla 开发者本地化实践](https://github.com/mozilla-l10n/documentation/blob/main/src/localization/dev_best_practices.md)

## 术语与原文保留

`translations/glossary/zh_CN.toml` 是强制术语的编辑源。翻译前查同一概念在核心 Help、现有界面及相关工具包中的用法。同词异义时按所属 domain 和 `msgctxt` 处理。新增或调整术语时，记录英文词、对象、首选写法、适用范围和例句。先核对对其他词库与 Help 的影响，再更新规则。[项目术语表](../translations/glossary/zh_CN.toml) · [GNOME 翻译项目的术语表建议](https://wiki.gnome.org/TranslationProject/LocalisationGuide)

| 概念 | 项目写法 | 示例 |
| --- | --- | --- |
| Neovim `Buffer`、`Window`、`Register` | 遵循现有 `preserve` 规则和对应文件的大小写约束。首次介绍时可以用中文解释对象的用途 | 「Buffer 保存当前编辑的文本。」 |
| 调试器的 CPU registers | 按调试器语义使用「寄存器」，沿用术语表中 CodeLLDB 的限定范围 | 「查看 CPU 寄存器」 |
| `diagnostic`、`code action`、`workspace` | 在语言服务的用户界面中用「诊断」「代码动作」「工作区」 | 「显示光标下的诊断」 |
| `breakpoint`、`stack frame`、`continue` | 在调试界面用「断点」「栈帧」「继续执行」 | 「删除断点」 |

命令、选项、键位、API、Help tag、配置键、代码、路径、URI、错误码和协议标识按原文写入译文。项目文件名、用户输入、日志和工具协议数据直接取自原始数据。译词只用于能够确认来源和用途的显示文字。文档中的英文技术名也可以作为检索入口。

## PO 与动态消息

1. 在固定上游版本中找到实际显示的原文。用 `#:` 记录源码位置。缺少可引用源码的工具消息可引用保存的真实运行记录，注明工具版本、复现输入和原始输出。
2. 目录按所属插件或工具使用独立 domain。采用稳定的 `msgctxt` 区分标题、通知、状态和其他语义，保留 `msgid` 的实际文字。用 PO 注释说明触发位置、容易混淆的含义、占位符的用途与示例值，以及布局限制。[GNU gettext 手册的 PO 文件格式](https://www.gnu.org/software/gettext/manual/gettext.pdf)
3. 将完整的短句作为翻译单元，让译文可以自然组织语序。项目 UI 目录的 `{name}` 占位符可调整位置，名称、出现次数和含义要一致。非位置型 printf 占位符沿用原顺序、类型和格式规格，保留 `%%` 等转义。每条 UI 目录消息使用一种占位语法。UI 目录和核心补充 PO 每条使用一个 `msgstr`，计数依靠现有消息模板。[Mozilla 开发者本地化实践](https://github.com/mozilla-l10n/documentation/blob/main/src/localization/dev_best_practices.md)
4. 核心 gettext 保留实际查找键、原有格式标志、`E###:` 或 `W###:` 前缀、宏占位符及控制字符。涉及欢迎页、提示符或对齐填充的空白按源键和渲染契约处理。发现上游 PO 和运行时键漂移时，按固定源码或二进制证据更新 native 清单，并验证真实消息。[核心 gettext 维护流程](../CONTRIBUTING.md#核心-gettext-消息)

以下条目展示了已有的源码引用和由两个 `%s` 构成的提示。第一个参数是会话文件路径，第二个是底层错误说明。

```po
#: lua/nvim-tree/session.lua
msgctxt "notification"
msgid "Failed to write session file (%s): %s"
msgstr "无法写入会话文件（%s）：%s"
```

## 中文 Help

上游 Help 以固定提交和源文件摘要为基线。逐段翻译说明，并核对条件、默认值、例外和警告。保留上游 tag、`|链接|`、示例块、文件头和 modeline，使用 `:helptags` 生成 `tags-cn`。tag 与后续中文说明之间留 ASCII 空格或 Tab。新增项目自己的操作指引时，可以按任务组织内容并指向已有的 Help tag。核心 Help 和可选包按对应的结构与索引检查交付。[Neovim 翻译 Help 格式](https://neovim.io/doc/user/helphelp/#help-translated) · [项目 Help 保真契约](../tools/HELP_TRANSLATION_CONTRACT.md)

## 审校与发布检查

1. **核对语义。** 对照源版本和实际触发路径，核对对象、操作后果、术语、默认值和动态参数。上游措辞、参数或用途变更时重审受影响的词条。机器生成或 `fuzzy` 译文按草稿处理，经人工核对后提交正式译文。发布目录中的译文应已审校并填写完整，待补项记录为缺口。
2. **检查结构。** UI 和工具目录运行 `make check-translations`。核心消息运行 `make check-native`。Help 按贡献指南生成并检查 tag、链接和示例块。第三方适配运行 `make check-adapters`，并按清单执行受影响适配器的固定上游场景。重建发布资源后运行 `make check-resources check-reproducible`。[贡献流程](../CONTRIBUTING.md) · [测试与质量门禁](testing.md)
3. **在实际界面复核。** 从用户命令或键位复现成功、失败及英文回退。检查中英混排、窄屏、计数、冲突的同名文本、选择和跳转。宽度以终端显示列判断，光标和高亮按接入 API 所用的坐标验证。目录通过机器检查后，再凭实测场景说明该工作流的可用程度。

评审说明至少给出上游版本、受影响的界面或 Help 主题、实际执行的检查，以及待审或回退的内容。按工作流更新覆盖记录，让用户能判断目前可以用中文完成哪些环节。[完整中文工作体验的验收设计](architecture.md#完整中文工作体验)

## Clang 工具链措辞

使用「标识符」「形参」「实参」「约束」「实例化」「目标三元组」和「修复编辑」。保留 `ABI`、编译选项、检查名和语言关键字。模板的参数重排后应保留标识符、类型、嵌套诊断、路径和引号内项目文字。合成变体要复验实际 Lua 规则，来自 `#error`、注释、代码片段和修复替换的原文字段应有碰撞样例。
